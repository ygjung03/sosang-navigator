# 소상공인 상황 진단·정책 내비게이터

> 2026 금융 AI Challenge 출품작
> 매출 자료(POS)와 몇 가지 값만 받으면, AI가 재무 상황을 대신 계산해 **지금이 어떤 국면인지** 판단하고
> 그 국면에 맞는 지원 정책을 자격·중복·시점까지 따져 **어떤 조합이 가장 유리한지** 비교·설명한다.

---

## 핵심 아이디어

성격이 다른 지원(융자·보조금·채무조정)은 "지원금액"으로 줄세울 수 없다.
융자 7천만원의 "지원금액"은 갚아야 할 돈이라 허수다.
대신 **월별 현금흐름을 36개월 시뮬레이션**하면 셋이 같은 축에 올라온다.

**평가 축 2개 (동등하게 취급)**

| 축 | 의미 | 방향 |
|---|---|---|
| 생존 개월수 | 현금 잔고가 0이 되는 시점 | 클수록 좋음 |
| 30개월 후 순부채 | 그 시점의 총 부채 잔액 | 작을수록 좋음 |

두 축은 트레이드오프 관계이므로 코드가 단일 최적을 정하지 않는다.
축별 순위를 각각 매겨 상위 후보를 합집합으로 넘기고, 최종 선정은 LLM이 국면 맥락으로 한다.

## 디렉토리 구조

```
sosang-navigator/
├── core/
│   ├── loader.py       정책 JSON → '후보' 단위 전개
│   └── cashflow.py     현금흐름 엔진 (현금효과 6종 분기)
├── data/
│   └── policies_all.json   층2 구조화 정책 데이터
├── docs/
│   ├── planning.md         설계 문서 (구조·원칙·미정 사항)
│   ├── inquiries.md        기관 확인 필요 24문항
│   └── sources/            정책 데이터의 1차 근거인 공고문 원본 + 인덱스
├── tests/
│   └── test_cashflow.py    엔진 검증 (pytest 없이도 실행 가능)
├── .env.example        API 키 템플릿 (.env는 커밋 금지)
└── requirements.txt
```

> **파일명은 ASCII로 통일한다.** 한글 파일명은 macOS(NFD)와 Windows·Linux(NFC)의
> 유니코드 정규화 방식이 달라 같은 파일이 다르게 인식될 수 있고,
> Windows에서 클론할 때 인코딩이 깨질 수 있다.

### 아직 없는 것 (다음 작업)

- `core/combos.py` — 조합 생성 (문법 제약: 융자1·채무조정1·보조금2)
- `core/metrics.py` — 함정 3종 판정

## 데이터 구조

`policies_all.json`은 **정책 → 후보** 2계층이다.

- **정책(policy)** — 자격 판정의 단위 (업종·국면·신용점수·매출요건)
- **후보(candidate)** — 시뮬레이터가 소비하는 원자적 계산 단위

같은 자금이라도 **상환조건이 다르면 별개 후보**다.
1년거치는 13개월차, 2년거치는 25개월차, 만기일시는 24개월차에 상환이 시작되어
두 축 값이 크게 달라지고 순위가 뒤집힐 수 있기 때문이다.
조합 생성도 정책이 아니라 후보 단위로 이루어진다.

### 현금효과 6종

| 현금효과 | 처리 |
|---|---|
| `신규유입` | 지급 시점에 +금액. 융자면 거치 종료 후 매월 −상환액 |
| `대환전환` | 유입 없음. 기존 고금리 부채를 저금리로 옮겨 월 상환액을 낮춤 |
| `부채감면` | 유입 없음. 원금이 감면되고 새 조건으로 재조정 |
| `상환유예` | 유입 없음. 원금 감면 없이 상환기간만 연장해 월 상환액을 낮춤 |
| `비용감면` | 특정 비용 항목에만 쓰는 바우처. 해당 월 고정비 감소 |
| `없음` | 순위 대상 제외. 부가 추천으로만 안내 |

`_순위제외: true`인 후보는 2축 어디에도 반영되지 않아 조합에서 빠진다
(컨설팅, 용도가 묶인 사업화자금 등). 각 후보에 `_순위제외근거`가 달려 있다.

## 실행

의존성 없이 표준 라이브러리만으로 동작한다 (시뮬레이터 단계).

```bash
# 정책 데이터 요약
python -m core.loader

# 현금흐름 엔진 검증
python -m tests.test_cashflow
```

Streamlit UI 단계로 넘어가면:

```bash
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env      # API 키 입력
streamlit run app.py
```

## 설계 원칙

1. **계산은 코드, 맥락 판단은 LLM.** 시뮬레이션·조합 생성·2축 계산은 코드(정확·재현), 최종 선정·함정 서술·설명은 LLM
2. **정량으로 고를 수 없으면 고르지 않는다.** 상환조건처럼 두 축이 트레이드오프인 선택은 단일 최적으로 단정하지 않고 모든 경우를 후보로 전개
3. **두 축은 동등.** 국면별 가중치·정렬 축 우선순위를 코드에 넣지 않는다
4. **명백한 것만 판정, 회색지대는 숫자만.** 근거 없는 임계값을 만들지 않는다
5. **경고는 적을수록 신뢰.** 잘못된 경고 1건이 서비스 전체 신뢰를 무너뜨린다
6. **가정은 코드에 명시한다.** `core/cashflow.py` 상단 ASSUMPTIONS 참조

## 데이터 정확도에 대한 입장

- 36개월 현금흐름은 **예측이 아니라 "현재 추세가 유지된다는 가정 하의 시나리오"**다. 절대값의 정확도는 주장하지 않는다
- 모든 조합에 동일한 매출 가정을 적용하므로, 절대값이 빗나가도 **조합 간 상대 순서는 상대적으로 안정적**이다
- 정책 데이터는 **공고문 원문 대조를 원칙**으로 하고, 2차 출처로만 확인된 값은 `_검증상태`에 그대로 적어둔다
- 기관 확인이 필요한 항목은 `docs/inquiries.md`에 24문항으로 정리돼 있다
